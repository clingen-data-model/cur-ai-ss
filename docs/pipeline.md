# The extraction pipeline in detail

What each step does and why it does it that way, the curator note and quick
run that travel down the task graph, and how the sharded workers claim and
retire attempts. CLAUDE.md has the one-line version of each; the task graph
itself is `TaskType` and `TASK_SUCCESSORS` in `lib/tasks/models.py`, and the
handlers are `TASK_HANDLERS` in `lib/tasks/handlers.py`.

## Steps

### PDF Parsing

Parses PDF, extracts metadata, markdown content, tables. The Docling conversion is the only model run of our own and takes the VM minutes per paper; `parse_content` sends it to the PDF parsing service on a Cloud Run GPU instead, the PDF and the converted document passing through a bucket rather than an HTTP body (`PDF_PARSING_SERVICE_URL`, `PDF_PARSING_EXCHANGE_BUCKET`, set in the deployment since 2026-11-02; `docs/cloud-run-parsing.md`), everything after the conversion staying in the worker. What stays allocates a few hundred MB of short-lived buffers that glibc keeps after Python frees them (a worker went from 477 MB to 1,074 MB across its first parse on 2026-11-09 and stayed there), so the handler calls `release_freed_memory` (`lib/core/memory.py`, `malloc_trim`) after each parse, which returns about two thirds of it

### Paper Classifier

Decides whether the paper has identifiable cases for the gene; a paper judged not relevant gets the `FailedPaperRelevancy` tag and no successors. The verdict is stored with its basis (`papers.is_paper_relevant_evidence`, migration `d4e8f1a2b3c5`; until 2026-10-29 only the bool was kept and the basis lived in the task's conversation), and the paper page shows it in a notice above the tabs (`PaperRelevanceNotice.tsx`) with the re-run dialog opened on the classifier; a paper classified before the column shows no basis until the classifier runs again

### Individual Extraction

Identifies patients, demographics, proband status

### Figure Description

Shows every figure to the vision model, which classifies it against the readable kinds (`FigureKind` in `lib/models/figure.py`: pedigree, chromatogram, gel, copy-number plot, read pileup, karyotype or FISH) and describes the ones that match; one `figure_descriptions` row per described figure, carrying the caption the model was shown (`caption`, the alt text of the figure's `[figure-N] ![caption](...)` line in anchored.md, which is where Docling's caption-to-picture link is transcribed at parse time; where Docling linked none, the parser's walk looks at the one part right under the picture and, if `_legend_item` accepts it (one visible heading or paragraph, not a list item, whose text opens like a figure label: `is_figure_legend`), folds it into the figure line as a Docling caption would be, alt text and caption boxes, marks the anchor `caption_adopted`, and skips the part so it is not printed twice; the comment above `_legend_item` in `lib/misc/pdf/anchors.py` spells out the four ways Docling's link fails on dev and the five steps of the rule, which recovered 9 of dev's 24 uncaptioned described figures on 2026-10-27, all below their picture; parsing runs first with no model, and the Figure Description step reads what it wrote: a readable figure whose line still carries no caption is asked of the vision model, `find_legend`, shown the headings and paragraphs within ten blocks either side (`figure_neighbourhoods`) and answering with a block id, a transcription of a legend drawn inside the image, or none; both describing prompts also ask for a legend printed inside the image to be transcribed at the top of the description (`LEGEND_IN_IMAGE_SECTION`, since 2026-11-03: the layout model had cut the first column of one paper's legend into the picture and the parser linked the second column as the caption); a legend further away than that is not found and the figure has no caption; the answer goes on the row, never into anchored.md; this settled the other 15 on dev, panels of one figure getting their own panel labels; both describing prompts are shown those same surrounding blocks every time (`_surroundings_section`, since 2026-10-30), because Docling often links only a legend's title line and leaves its body, where marks like an asterisk are defined, as the paragraph under the figure (MAG paper, PMID 32629324), and a model reading what is around the figure beats a parser rule for each way a legend comes apart; `caption_source` (`CaptionSource`: Docling, Adjacent text, Model chose, Model transcribed) records which way each row's caption came, `Anchor.caption_adopted` in anchors.json telling the first two apart for a parse-time adoption; rows from before migration `b7e2f9c4d6a1` are filled by `lib.bin.backfill_figure_captions` from what `paper_figures` would hand a re-run (the figure line's caption, else the same question), `--no-model` to skip the question; a stored caption the figure line lacks is spliced under the line for the agents, `splice_figure_descriptions`). Not an agent (`lib/agents/figure_describer.py`), so it has no conversation to ask and curator notes go into its vision prompts. Every paper-reading agent then gets each description spliced into the paper text as a quoted block under its `[figure-N]` line (`paper_text` in `lib/tasks/handlers.py`, `lib/misc/pdf/figure_text.py`); the `/document` endpoint serves the same text, a quote from a description checks out against its figure, highlights the picture in the PDF view and both the figure and the span in the Markdown view

### Variant Extraction

Extracts genetic variant information

### Variant Harmonization

Normalizes variants to standard formats. Its input is the variant row's plain fields (no evidence text), so anything it needs from the paper has to be in a field. Older papers number nucleotides from a GenBank mRNA start rather than the ATG (paper 109, PKD1, runs 211 ahead); the agent checks a position against its residue's codon window (residue N is c.3N-2..3N) before projecting, tries the window's three positions when the paper's is outside it, and rejects a registry allele whose consequence names another residue instead of storing it with a note (`C7696T` once came back as p.Leu2566Phe with an rsID). Extraction feeds that check by writing silent changes as `p.Ser1949=` and keeping a GenBank cDNA accession in `transcript`. A variant extracted as words alone ("deletion of exon 2", "arginine 66 to tryptophan") met no state's condition and came back null until 2026-11-06; State 0 now infers the terms the words could mean (hgvs_c candidates, protein forms, ClinVar search names) and the existing states consume them as the fields they stand in for, the lookups being the check, confidence low and the inference stated in basis

### Variant Annotation

Adds annotations (SpliceAI, etc.)

### Phenotype Extraction + HPO Linking

Links phenotypes to HPO ontology terms. Phenotype extraction is queued per patient when their demographics completes, for every patient but those it marked Unaffected (a curator can still queue it for anyone); HPO linking follows for every phenotype the run produced that the HPO link cache did not already link, whatever the patient's variants (it used to wait for a variant occurrence, which saved ~15 calls a paper and left a manual phenotype run linking nothing)

Measured values and thresholds (since 2026-11-23). On dev, 482 of 11,644 HPO links had a number in their basis. Most came from HPO's own definitions, but the lipid papers (33, 36, 38) had bare lab values ("LDL cholesterol 125 mg/dL") linked to an increased or decreased term on reference ranges the agent recalled ("HDL ≥60 is increased", "total cholesterol 133 is low"), "HDL cholesterol 44 mg/dL" went to Decreased in one link and Abnormal in another, and a hearing band was cited as 41-70 dB where HPO says 41-60. About 830 HPO terms carry a numeric threshold, a third of them only in the term's comment, which the agent was never shown; the definition reached it as a `Definition` repr. Now every term the agent sees (candidates, search results, lookups, parents, children) comes through `describe_term` (`lib/reference_data/hpo.py`) with its definition text and comment. The prompt allows a number in the basis only from the concept or HPO's text, links a bare value to the "abnormal" parent with an unresolved flag, and raises a mismatch flag for a value outside the range HPO gives the term. Upstream, phenotype extraction writes a measured finding with its direction in words ("low <analyte> (<value>)") and leaves out a normal value; the 2026-10-29 rule still extracts a value judged against a threshold the paper does not state, as uncertain and flagged inferred. Where HPO only says "limit of normal" (most blood levels), the paper's words have to decide. The HPO link cache reuses every link, measured concepts included: links made before this change are replaced by re-running the paper's phenotype extraction with a curator note, which skips the cache, so every phenotype goes through the agent and its new link becomes the cache's entry for that text.

### Individual Variant Occurrences

Links patients to their variants with inheritance info. Waits on Individual Extraction and Variant Extraction, not on demographics, which it never reads; segregation (evidence extraction, then the computed analysis) is the step that waits on the last per-patient demographics run, since it reads affected status (`TASK_SUCCESSORS` in `lib/tasks/models.py`)

### Extraction Verification

Runs once every other task of the paper has settled (queued by the worker, not by a graph edge). First a model looks over the extracted individual and link values, with their basis and the text of the blocks they cite (not the paper), for values that should agree and do not, and raises `inconsistent` flags; a re-run replaces the open ones and keeps those a curator resolved, which the model is shown so it does not raise them again (`replace_flags(keep_resolved=True)`; every other source's re-run still deletes its resolved flags). Then it merges curator flags that raise the same decision more than once (`lib/tasks/extraction_verification.py`)

## Re-runs and curator notes

- **Skip Successors:** Check "Skip successor tasks" when queueing a task to run ONLY that task without triggering dependent tasks. Useful for debugging or manual reruns. The flag is stored in `tasks.skip_successors` and checked by the worker when a task completes.
- **Re-run all tasks:** the dialog's "All tasks" tab queues PDF Parsing (with "Also re-parse the PDF") or Paper Classifier through `POST /papers/{id}/tasks` like any other task; there is no separate endpoint or paper field. Every task descends from those two, and a task's `additional_context` comes down the successor graph: `enqueue_successors` copies it to every descendant of that run with `tasks.context_origin` naming the task it was given to, so a note on the root is the run-all note, and the note reaches every agent worded "given for this re-run of the whole paper" (`curator_note_section` in `lib/tasks/handlers.py`; for any other origin, "supplied to X and might also be relevant here"). A descendant starts fresh with the note as the last item of its first message (`with_curator_note`), after the cache-breakpointed paper block, instructions and data; figure description, which has no conversation, puts the labelled note in its vision prompts; phenotype extraction skips the HPO link cache while its run has a note, so the HPO agent actually sees it. A note only ever becomes a follow-up to the task's own conversation when it was given to that task and the task has a conversation to follow up on (`continues_conversation`); otherwise, including after a retry cleared the session, it goes into a fresh first message. A follow-up restates the task's data as it stands now (the patient JSON and proband, the family structure, the variant JSON, the phenotype, the MONDO target) ahead of the note, since a curator may have edited those rows since the first run and the conversation holds only the first run's copy (`build_followup_prompt`); the paper and the instructions are not resent, and the four handlers whose first message is the paper alone pass no data. The next enqueue of a descendant without a note clears it, so a note lives on one chain of runs: `papers.paper_global_additional_context`, the sticky paper-wide note it replaced, was dropped on 2026-10-22. PDF Parsing is not an agent and reads no note itself, but its successors get it.
- **Quick run:** `tasks.budget_model` (migration `c3d9e1f7a2b4`) runs the task and its successors on `EXTRACTION_BUDGET_MODEL`. The chat agent's queue tool does not set it. `EXTRACTION_BUDGET_MODEL` is the cheaper model a curator can pick for one run: the "Quick run" box in every re-run dialog sets `tasks.budget_model`, which comes down the successor graph like a curator note, and each handler whose agent runs on `EXTRACTION_MODEL` runs a per-run clone of it on this model instead (`agent_on_tier` in `lib/agents/model_factory.py`; linking and vision are unaffected). Unset, a quick run is an ordinary run. dev-caa sets `anthropic/claude-haiku-5-5`. The UI never names a model: the box says quick and lower-cost, and the task timeline marks rows that ran that way

## Claimed tasks and the sharded workers

everything the scheduler knows is in the `tasks` table, and since 2026-11-09 it is shared by `WORKER_COUNT` worker processes, each owning the papers whose id % `WORKER_COUNT` is its `WORKER_ID` (`shard_filter` in `lib/bin/worker.py`, on every query the module runs over the table; the deployment runs four as the systemd template instances `worker@0` .. `worker@3`, `worker_count` in the playbook, and a developer's defaults are one worker owning everything). A paper's whole pipeline runs in one process, and the concurrency limits are per process, so the PDF Parsing cap of 1 is four parses in flight against the pdf-parsing service's two instances. Each poll (every 5 s since 2026-11-03, one transaction, `_poll_and_schedule_tasks`) counts the shard's RUNNING rows against `GLOBAL_CONCURRENCY` and `TASK_CONCURRENCY`, and starts as many of its PENDING rows as fit: claiming a task is starting it (`start_attempt` stamps RUNNING, `started_at` and `tries`), so nothing waits in an in-process queue and a freed slot is refilled on the next poll. The per-(paper, type) fan-out gate is decided from the same table: a batch whose first attempt is RUNNING admits nothing more until an attempt of that batch has finished within `CACHE_WARM_S`. An attempt's lease runs from `started_at` (`lease_timeout_s`: 20 min by default, 30 min for PDF Parsing; never refreshed, so each must exceed the longest legitimate run of its type, and PDF Parsing has reached 15 min on a 44-page supplement); an attempt past it is retired: its coroutine is cancelled (the worker keeps a handle per live attempt in `_attempts`) and its row goes PENDING with its session cleared while retries remain, else FAILED. A cancel lands at the handler's next await, so thread-bound work such as a Docling parse runs to its end first; whenever the coroutine does get to its outcome, it finds the row's status or tries moved on and drops it (`execute_task` only writes for the attempt it was started as). `TaskStatus` is PENDING, RUNNING, COMPLETED or FAILED; QUEUED, the old claimed-but-parked status, was dropped on 2026-10-26 (migration `7c1e5a9d3b2f` turns leftover rows PENDING). There is one worker process per shard, and the worker relies on it: on a shutdown signal it stops polling and sweeps *every* claimed row of its shard back to PENDING (session cleared) or FAILED on its last try, and it runs the same sweep before its first poll, so a crash or a kill leaves nothing claimed past the next start (`_sweep_claimed_tasks`). Two workers with the same shard, or started with different `WORKER_COUNT`s, would steal each other's live tasks, which is why the count is written into every unit instance and the old single `worker` unit is disabled by the playbook.

## Models and providers

- `EXTRACTION_MODEL`, `LINKING_MODEL`, `VLM_MODEL` take `<provider>/<model>`; the defaults are in `lib/core/environment.py` and dev-caa's values in `infrastructure/ansible/templates/env.j2`.
- `LINKING_MODEL`: The model the two ontology-linking agents (HPO, MONDO) run on, same form (default: `openai/gpt-5.6-luna`; dev-caa sets `anthropic/claude-haiku-5-5`). Every other agent is on `EXTRACTION_MODEL`, which dev-caa moved to `anthropic/claude-sonnet-5-5` on 2026-10-22: the Haiku 5.5 trial showed its HPO links match Sonnet's, while no prompt fixed its paper-reading failures (skipped pedigree members on paper 108, a cohort-wide testing method applied to 3 of 11 subjects in three runs where Sonnet gave 11 of 11 in three). Linking is many small calls per paper, extraction a few large ones, so this is where the cost split pays
- `VLM_MODEL`: dev-caa was on Fable 5.1 until 2026-10-19, when Fable's safety classifier deterministically refused a table-correction call on paper 106 and failed its PDF parse. A classifier refusal through LiteLLM now raises `ModelDeclined` (`lib/agents/model_factory.py`) on the first turn instead of looping to `MaxTurnsExceeded`; table correction catches it and marks the table unrecovered.
- Providers: required whenever a configured model names `anthropic/`. `anthropic/` routes through LiteLLM; `openai/` goes to the agents SDK's default provider. The two settings may name different providers, so vision and extraction can be pointed at different providers independently. Extraction used to be pinned to OpenAI because `responses_api_model()`'s server-side `conversation_id` had no Anthropic equivalent; that dependency is gone now that `lib.tasks.agent_session` gives every task its own provider-agnostic `SQLiteSession` (see `docs/anthropic-migration.md`), so extraction can run on Claude too -- verified live against the MASP1 test paper (PMID 26419238) before flipping dev-caa to it
